## Punto 2 — Pipeline consume `openspec status` como fuente del estado

### Decisión de dirección (ya confirmada con vos)
- Cablear `openspec status` **antes** que el rediseño visual (punto 3).
- Este change **no** toca la barra de fases ni `derivePipelineNextAction`: sólo hace llegar el grafo real hasta el renderer, para que el punto 3 lo consuma. La barra sigue mostrando el modelo viejo por ahora (no se rompe nada).

### Qué hace el change `consume-openspec-status`
Hace llegar el grafo de artefactos con estados `blocked`/`ready`/`done` desde el CLI hasta el snapshot del renderer, siguiendo las tres convenciones existentes (wrapper de CLI → reader con dep inyectada → tipo propagado por el snapshot).

### Archivos a tocar

**Main / tipos compartidos**
1. `electron/pipeline/openspec-cli.ts` — nueva función `statusOpenSpecChangeWithCli(repoPath, changeId): Promise<OpenSpecChangeStatusResult>`. Reutiliza `CLI`, `execFileAsync`, `CHANGE_ID_PATTERN`, el try/catch con prioridad `stderr/stdout/message` y el env `OPENSPEC_TELEMETRY_DISABLED`. Invoca `['status', changeId, '--json']`, parsea `JSON.parse(stdout)` y mapea a los tipos nuevos. En fallo de ejecución devuelve `{ available: false, artifacts: [], applyRequires: [] }` (no propagar excepción: "no saber no es saber que no", mismo criterio que `validate → 'unknown'`).
2. `types/pipeline/index.ts` — nuevos tipos:
   - `OpenSpecArtifactState = 'blocked' | 'ready' | 'done'`
   - `OpenSpecArtifactStatus = { id: string; state: OpenSpecArtifactState; missingDeps: string[] }`
   - `OpenSpecChangeStatus = { available: boolean; artifacts: OpenSpecArtifactStatus[]; applyRequires: string[]; isComplete: boolean }`
   - Agregar campo **opcional** `status?: OpenSpecChangeStatus | null` a `OpenSpecChangeEvidence` (opcional para no romper snapshots SQLite viejos).

**Reader (evidencia)**
3. `electron/pipeline/repo-evidence-reader.ts` —
   - Agregar `statusOpenSpecChange?` a `RepoEvidenceReaderDependencies` (línea ~24-30).
   - En el loop por change activo (línea ~186-220), invocar `statusOpenSpecChange` **sólo para el change seleccionado** (`isSelected`), igual que `validate` y `artifacts`. Si la dep no está o falla, el campo queda `null`.
   - Cablear el default en el constructor (~línea 119): `statusOpenSpecChange: statusOpenSpecChangeWithCli`.

**Renderer (tipos y snapshot)**
4. `components/pipeline/pipeline-view-state.ts` — agregar `status?: OpenSpecChangeStatus | null` a `OpenSpecChangeSummary` (espejo del campo nuevo de `OpenSpecChangeEvidence`).

### Lo que NO hace este change
- No toca `derivePipelineNextAction`, `lifecycle()`, la barra de fases ni `PipelineNextStepGuide`. Siguen derivando del modelo viejo. Ese es el punto 3.
- No agrega canal IPC nuevo: el grafo viaja dentro del `OpenSpecChangeEvidence.status` del snapshot existente (`pipeline:get-snapshot` / `pipeline:snapshot-updated`). No hay más round-trips.
- No agrega dependencias. Reutiliza `execFileAsync` existente.

### Tests
- **Wrapper CLI** (`electron/__tests__/pipeline-openspec-cli.test.ts` — archivo nuevo o extender uno existente si lo hay): parsea un stdout JSON fixture y devuelve el grafo mapeado; en fallo de ejecución devuelve `{ available: false, ... }` sin lanzar. No spawnea el CLI real (se prueba la función de parseo mapeando stdout, o se inyecta el runner).
- **Reader** (`electron/__tests__/pipeline-repo-evidence-reader.test.ts`): con una dep `statusOpenSpecChange` inyectada que devuelve un grafo fixture, el change seleccionado trae `status` y los no seleccionados lo traen en `null` (mismo patrón que `artifacts` y `validation`).
- **Costo** (`electron/__tests__/pipeline-refresh-cost.test.ts`): extenderlo para fijar que `statusOpenSpecChange` se invoca una sola vez y sólo para el seleccionado — misma red que la que ya cubre `validateOpenSpecChange`.
